# 顶层规则

1. 不要假定用户总是正确的；遇到不明确、不合适、与事实或契约冲突的需求，先确认、给建议、征询同意，再执行。
2. 用户提出每个改进点时，应抽象背后的稳定问题、约束与同类场景，给出最小但完整的系统性方案；扩大范围、改变契约或增加风险前必须先征询同意。
3. 做任何代码修改前，先找到对应的设计文档并理解契约；若缺失对应契约，先补最小必要文档。
4. 任何影响对外行为的改动，都必须同步检查并更新 `design/` 与 `tests/`。
5. 设计文档、测试用例、AGENTS 规则都不要写得过细、过碎、过度绑定实现。
6. 完成一个特性后，应主动检查同区域是否存在明显技术债；若存在且风险可控，优先顺手重构。
7. 无论何时都要考虑多语言，不要把特定语言硬编码到代码、测试锚点或契约中。

## 工作入口

- 优先理解模块职责、公开接口、数据流转、依赖边界，不要先钻内部实现。
- 若改动影响对外接口、页面路由、核心组件 Props、稳定数据结构或用户主流程，必须在同一次任务中同步更新设计文档与测试。
- 若只是内部重构且对外契约不变，不应为了配合实现去改设计文档或契约测试。
- 若原测试因内部重构失败，优先视为契约被破坏。

## 需求澄清与同意

- 目标、范围、验收标准不明确时，先说明不确定点并确认。
- 用户描述与代码、文档、测试、线上约束或已知事实冲突时，先给出证据和推荐方案。
- 用户要求可能破坏对外契约、数据安全、权限边界、隐私、可访问性、多语言能力或核心用户旅程时，必须等待明确同意。
- 用户指定实现方式明显不适合当前结构，或存在更低风险做法时，先说明建议并征询同意。

## 设计文档原则

- `design/` 是契约说明书，不是实现笔记。
- 文档应说明模块职责、对外契约、数据流转、依赖边界。
- 不要记录内部函数、临时变量、缓存 key、CSS 类名、框架技巧或实现步骤。
- 不要把具体中文或英文文案写成契约本身。
- 优先用表格、列表、流程图描述稳定边界。

## 测试原则

- 测试是重构安全网，首先锁定行为与契约，而不是锁定实现。
- 优先保留少量高价值 E2E，优先编写接口/集成测试；单元测试只用于复杂且稳定的规则、算法或边界条件。
- 不要断言私有变量、内部调用顺序、临时状态、CSS 类名、DOM 层级、像素级布局或整页快照。
- 前端测试优先使用可访问性角色、稳定属性或 `data-testid`。
- UI 样式和静态文案调整通常不应导致契约测试失效。

## 多语言原则

- 代码、设计文档、测试锚点、数据结构与对外契约都不要默认只有一种语言。
- 不要把具体中文或英文文案当作稳定契约；文案可以变化，语义和结构才是更稳定的边界。
- 前端交互、可访问性名称、测试选择器和错误语义应避免依赖某一种展示语言。

## Language & Encoding

- 使用中文回复和编写文档。
- 代码注释使用英文编写。

## Indentation

- 新项目使用 4 个空格缩进。
- 现有项目检测并遵循现有风格，包括 `.editorconfig`、`pyproject.toml`、`.stylua.json`、`.clang-format` 等。

## ASCII Diagrams

ASCII 框图内的内容必须使用英文，禁止中文。中文字符在 GitHub 等宽字体中宽度不一致，容易导致框图对齐错位。

详细规范：`assets/rules/shared/ascii-diagrams.md`

## Codeact Mode

对于复杂流程，优先编写并执行代码脚本，而非直接调用工具。适用场景包括多步骤数据处理、转换、循环、条件分支、状态跟踪或错误恢复。

详细指南：`assets/rules/shared/codeact.md`
