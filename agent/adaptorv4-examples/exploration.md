# 探索型任务样例

## 类型定义

**特征**：目标明确 + 路径不明确 + 需要对比/评估/设计

**OODA重点**：Orient + Decide（定向与决策）

**场景**：技术选型、架构设计、根因排查、方案评估

**起点**：确定候选范围 → 确定评估维度 → 并行各候选调研 → 对比表 + 推荐

---

## 深度临界点判断

| DEPTH | 侧重点 | 深度临界点 |
|-------|--------|------------|
| 1-2 | 对比 | 搜索最新数据，确保版本准确 |
| 3 | 评估 | 双向案例（成功+失败）|
| 4 | 可行性 | 代码级依赖分析 + 团队能力评估 |
| 5+ | 风险 | 组织因素 + 失败案例研究 |

**浅答基线**：凭记忆回答。本系统搜索最新基准数据，确保版本准确；深入时发现关键约束和迁移成本。

## 经验传递示例（DEPTH 2）

### 任务

> 我们要把消息队列从 RabbitMQ 换成 Kafka，你觉得值得吗？

### 树结构

```
L1 Adaptor (DEPTH=2)
├── 循环 1：Adaptor-A (DEPTH=1) — 现状调研
│   ├── Worker: 当前 RabbitMQ 使用模式 + 真实痛点
│   └── Worker: 死信队列和消息优先级依赖
├── 循环 2：Adaptor-B (DEPTH=1) — 对比分析
│   ├── Worker: Kafka vs RabbitMQ 性能基准
│   └── Worker: 消息语义差异（死信/优先级支持）
└── 循环 3：Worker — 综合建议报告
```

### 阶段1：并行调研

**委托**：
```markdown
[目标-验证声明]
目标: 调研当前 RabbitMQ 使用痛点和 Kafka 兼容性
验证类型: 检查清单 + 结论挑战
验证方式: 痛点统计 + 功能兼容性对比
PASS条件: 两项调研完成，数据有来源

温度策略 temperature=0.25 | 理由：调研类任务，需数据准确性和逻辑严谨
```

**Worker 返回关键发现**：
- 真实痛点：死信队列消息堆积，非吞吐量问题
- Kafka：不原生支持死信队列和消息优先级

### 阶段2：补充验证（复用 Worker）

**注入共享上下文**：
```markdown
[共享上下文 - 来自阶段1]
- 真实痛点: 死信队列消息堆积，非吞吐量
- Kafka: 不原生支持死信队列

基于你之前的发现，补充评估：
- 实现 DLQ topic 的工作量
```

**Worker 返回**：迁移成本高，需要重写 300+ 行业务逻辑

### 父级结论挑战

```
Q: 吞吐量优势不能弥补死信队列功能的缺失吗？
A: 当前痛点不是吞吐量，迁移后反而增加开发成本。

Q: 是否可以通过业务层实现 DLQ topic 解决？
A: 可以，但需要重写现有逻辑，且无 RabbitMQ 的特性。
```

**最终结论**：不支持迁移，优先解决当前死信队列堆积问题。

│   │   ├── Worker: 业务复杂度分析

## 向下拓展方法

DEPTH > 5 按以下模式拓展：

### 拓展方向

| 维度 | DEPTH +1 | DEPTH +2 | DEPTH +3 |
|------|----------|----------|----------|
| 候选范围 | 更多备选方案 | 非主流方案 | 跨领域借鉴 |
| 评估维度 | 成本/风险 | 组织/文化 | 长期演进 |
| 验证方式 | POC 验证 | 小范围试点 | 第三方评审 |
| 决策支持 | 敏感性分析 | 情景规划 | 决策树与概率 |

### 拓展原则

- 探索型任务的核心是降低不确定性
- 每增加一层，应减少一个关键假设
- 最终输出应能回答"为什么选择 A 而不是 B"

### 验证类型递进

| 层级 | 验证类型 |
|------|----------|
| L1-L2 | 检查清单 + 结构化输出 |
| L3-L4 | 结论挑战 |
| L5+ | POC 验证 + 第三方评审 |
