# 探索型任务样例

## 类型定义

**特征**：目标明确 + 路径不明确 + 需要对比/评估/设计

**OODA重点**：Orient + Decide（定向与决策）

**典型场景**：技术选型、架构设计、根因排查、方案评估

**默认起点结构**：确定候选范围 → 确定评估维度 → 并行各候选调研 → 对比表 + 推荐

---

## DEPTH 1：选择 JSON 库

> 用户：Go 项目选一个 JSON 库，哪个好？

### 树结构

```
L1 Adaptor (DEPTH=1)
├── Worker: 搜索 Go 主流 JSON 库性能基准
└── Worker: 功能对比（泛型支持/自定义序列化/错误处理）
```

### 核心要点

- **简单对比**：性能 + 功能两个维度
- **搜索优先**：性能数据必须用当前版本的基准测试
- **推荐明确**：给出结论，不是"都差不多"

### 深度临界点

浅答系统凭记忆回答。本系统搜索最新基准数据，确保版本准确。

## DEPTH 2：消息队列技术选型

> 用户：我们要把消息队列从 RabbitMQ 换成 Kafka，你觉得值得吗？

### 树结构

```
L1 Adaptor (DEPTH=2)
├── 循环 1：Adaptor-A (DEPTH=1) — 现状调研
│   ├── Worker: 当前 RabbitMQ 使用模式 + 真实痛点
│   └── Worker: 死信队列和消息优先级依赖情况
├── 循环 2：Adaptor-B (DEPTH=1) — 对比分析
│   ├── Worker: Kafka vs RabbitMQ 性能基准（外部搜索）
│   └── Worker: 消息语义差异（死信/优先级支持）
└── 循环 3：Worker — 综合建议报告
```

### 核心要点

- **痛点先行**：先调研真实痛点，迁移是手段不是目的
- **语义兼容**：业务对死信队列/优先级有依赖，这是关键约束
- **结论挑战**：吞吐量优势不解决死信配置问题

### 深度临界点

调研返回"Kafka 吞吐量是 RabbitMQ 40 倍"。浅答系统倾向支持迁移。
本系统挑战："吞吐量不是当前痛点，当前痛点是死信队列行为，而 Kafka 需要业务层实现"。结论不支持迁移。

## DEPTH 3：架构方案评估

> 用户：评估我们的系统是否应该采用事件溯源架构

### 树结构

```
L1 Adaptor (DEPTH=3)
├── 循环 1：Adaptor-A (DEPTH=2) — 现状分析
│   ├── Adaptor (DEPTH=1) — 业务特征
│   │   ├── Worker: 业务复杂度分析（状态转换/查询模式）
│   │   └── Worker: 合规要求（审计/时序查询需求）
│   └── Worker: 技术团队能力评估
├── 循环 2：Adaptor-B (DEPTH=2) — 事件溯源适配分析
│   ├── Adaptor (DEPTH=1) — 适用性评估
│   │   ├── Worker: 事件溯源成功案例（相似业务）
│   │   └── Worker: 事件溯源失败案例与教训
│   └── Worker: 迁移成本估算
└── 循环 3：Adaptor-C (DEPTH=1) — 综合评估
    ├── Worker: 收益/成本分析
    └── Worker: 分阶段引入路线图
```

### 核心要点

- **业务驱动**：从业务复杂度、合规要求出发
- **双向案例**：成功案例 + 失败教训
- **团队能力**：事件溯源需要团队有相应经验

### 深度临界点

DEPTH=2 可能只分析事件溯源的优势。DEPTH=3 多了团队能力评估 + 失败案例研究，避免盲目引入。

## DEPTH 4：系统迁移评估

> 用户：评估核心交易系统微服务化的可行性与迁移路线图

### 树结构

```
L1 Adaptor (DEPTH=4)
├── 循环 1：Adaptor-A (DEPTH=3) — 现状深度摸底
│   ├── Adaptor (DEPTH=2) — 代码与数据层分析
│   │   ├── Adaptor (DEPTH=1) — 模块边界与依赖
│   │   │   ├── Worker: 静态依赖图谱
│   │   │   └── Worker: 数据库表归属与跨模块访问
│   │   └── Worker: 共享状态、循环依赖识别
│   ├── Adaptor (DEPTH=1) — 运行时特征
│   │   ├── Worker: 各模块 QPS/延迟/错误率分布
│   │   └── Worker: 真实性能瓶颈识别
│   └── Adaptor (DEPTH=1) — 团队能力评估
│       ├── Worker: 测试覆盖率 + 部署流水线现状
│       └── Worker: 团队分布式系统运维经验
├── 循环 2：Adaptor-B (DEPTH=3) — 拆分方案设计与验证
│   ├── Adaptor (DEPTH=2) — 候选边界评估
│   │   ├── Adaptor (DEPTH=1) — 核心边界可行性
│   │   │   ├── Worker: 订单-支付跨服务事务分析
│   │   │   └── Worker: 同类电商微服务边界案例
│   │   └── Worker: 分布式事务方案对比
│   ├── Adaptor (DEPTH=1) — 迁移模式选型
│   │   ├── Worker: Strangler Fig vs Big Bang 案例研究
│   │   └── Worker: 现有集成测试覆盖率评估
│   └── Adaptor (DEPTH=1) — 风险识别
│       ├── Worker: 分布式事务失败场景枚举
│       └── Worker: 微服务迁移失败案例研究
└── 循环 3：Adaptor-C (DEPTH=2) — 路线图制定
    ├── Worker: 基于风险排序的分阶段迁移序列
    └── Worker: 先行能力建设计划
```

### 核心要点

- **代码级依赖分析**：跨模块数据库写入是拆分障碍
- **瓶颈根因**：真正瓶颈是读写分离问题，不是服务耦合
- **团队能力**：无分布式运维经验是关键风险
- **测试覆盖**：11% 覆盖率不支持 Strangler Fig

### 深度临界点

DEPTH=3 可能推荐"采用 SAGA 模式 + Strangler Fig 迁移"。
DEPTH=4 发现：
- 当前代码无幂等设计，SAGA 不可行
- 测试覆盖率 11%，Strangler Fig 的行为等价验证假设不成立
- 团队无分布式运维经验

最终建议：不迁移。先解决读写分离痛点，建立前置条件后再评估。

## DEPTH 5：企业级技术转型评估

> 用户：我们想从传统单体架构全面转向云原生架构，评估可行性与实施路线

### 树结构

```
L1 Adaptor (DEPTH=5)
├── 循环 1：Adaptor-A (DEPTH=4) — 现状全景分析
│   ├── Adaptor (DEPTH=3) — 技术栈分析
│   │   ├── Adaptor (DEPTH=2) — 架构现状
│   │   │   ├── Adaptor (DEPTH=1) — 应用架构
│   │   │   │   ├── Worker: 现有应用架构梳理
│   │   │   │   └── Worker: 技术债务清单
│   │   │   └── Worker: 数据架构现状
│   │   └── Adaptor (DEPTH=1) — 基础设施现状
│   │       ├── Worker: 部署模式分析
│   │       └── Worker: 运维工具链评估
│   ├── Adaptor (DEPTH=2) — 组织能力分析
│   │   ├── Adaptor (DEPTH=1) — 团队能力
│   │   │   ├── Worker: 云原生技能矩阵评估
│   │   │   └── Worker: DevOps 成熟度评估
│   │   └── Worker: 组织结构与决策流程分析
│   └── Adaptor (DEPTH=1) — 业务影响分析
│       ├── Worker: 业务连续性要求分析
│       └── Worker: 合规与安全要求梳理
├── 循环 2：Adaptor-B (DEPTH=4) — 云原生适配分析
│   ├── Adaptor (DEPTH=3) — 技术适配
│   │   ├── Adaptor (DEPTH=2) — 容器化分析
│   │   │   ├── Adaptor (DEPTH=1) — 容器化可行性
│   │   │   │   ├── Worker: 应用容器化障碍识别
│   │   │   │   └── Worker: 有状态服务处理方案
│   │   │   └── Worker: 镜像构建与管理策略
│   │   └── Adaptor (DEPTH=1) — 服务网格适配
│   │       ├── Worker: 服务网格选型分析
│   │       └── Worker: 现有服务改造工作量估算
│   ├── Adaptor (DEPTH=2) — 组织适配
│   │   ├── Adaptor (DEPTH=1) — 组织变革
│   │   │   ├── Worker: 平台团队组建方案
│   │   │   └── Worker: DevOps 流程改造方案
│   │   └── Worker: 培训与知识转移计划
│   └── Adaptor (DEPTH=1) — 成本分析
│       ├── Worker: 云资源成本估算
│       └── Worker: 人力投入与机会成本分析
├── 循环 3：Adaptor-C (DEPTH=3) — 风险与缓解
│   ├── Adaptor (DEPTH=2) — 技术风险
│   │   ├── Adaptor (DEPTH=1) — 迁移风险
│   │   │   ├── Worker: 大规模迁移失败案例研究
│   │   │   └── Worker: 云原生常见陷阱识别
│   │   └── Worker: 回滚策略设计
│   └── Adaptor (DEPTH=1) — 业务风险
│       ├── Worker: 业务中断风险分析
│       └── Worker: 合规风险识别
└── 循环 4：Adaptor-D (DEPTH=2) — 路线图与决策
    ├── Adaptor (DEPTH=1) — 分阶段路线图
    │   ├── Worker: 三年转型路线图
    │   └── Worker: 关键里程碑与验收标准
    └── Worker: Go/No-Go 决策建议
```

### 核心要点

- **全景视角**：技术栈 + 组织能力 + 业务影响
- **组织因素**：云原生转型失败多因组织而非技术
- **风险前置**：失败案例研究优先于成功案例
- **决策明确**：给出 Go/No-Go 建议，而非"看情况"

### 深度临界点

DEPTH=4 可能只分析技术可行性。
DEPTH=5 多了：
- 组织能力分析（决定转型能否落地）
- 大规模失败案例研究（避免常见陷阱）
- 业务连续性与合规风险（决定转型边界）

## 向下拓展方法

DEPTH > 5 的探索型任务，按以下模式拓展：

### 1. 候选范围拓宽
- DEPTH +1：增加更多备选方案
- DEPTH +2：增加非主流方案（可能发现隐藏机会）
- DEPTH +3：增加跨领域借鉴方案

### 2. 评估维度加深
- DEPTH +1：增加成本/风险维度
- DEPTH +2：增加组织/文化维度
- DEPTH +3：增加长期演进维度

### 3. 验证方式加严
- DEPTH +1：增加 POC 验证
- DEPTH +2：增加小范围试点
- DEPTH +3：增加第三方评审

### 4. 决策支持加强
- DEPTH +1：增加敏感性分析
- DEPTH +2：增加情景规划
- DEPTH +3：增加决策树与概率评估

### 拓展原则

- **探索型任务的核心是降低不确定性**
- **每增加一层，应减少一个关键假设**
- **最终输出应能回答"为什么选择 A 而不是 B"**
