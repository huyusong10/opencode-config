# 发现型任务样例

## 类型定义

**特征**：目标不明确 + 需要先定义问题 + 发现模式/机会

**OODA重点**：Observe + Orient（观察与定向）

**典型场景**：业务分析、数据挖掘、问题发现、机会识别

**默认起点结构**：初步摸底 → 确定分析框架 → 并行各维度深度调研 → 完整性检查 → 综合

---

## DEPTH 1：日志异常分析

> 用户：最近系统日志里有些奇怪的错误，帮我看看

### 树结构

```
L1 Adaptor (DEPTH=1)
├── Worker: 扫描近期错误日志，按类型统计
└── Worker: 识别异常模式（新出现的/频率突增的）
```

### 核心要点

- **模式识别**：不是看单条日志，而是看分布和变化
- **问题定义**：把"奇怪的错误"转化为具体的异常类型
- **输出明确**：给出问题清单和优先级

### 深度临界点

浅答系统列出错误。本系统识别异常模式：哪些是新出现的、哪些在增长。

## DEPTH 2：性能瓶颈定位

> 用户：系统最近变慢了，不知道为什么

### 树结构

```
L1 Adaptor (DEPTH=2)
├── 循环 1：Adaptor-A (DEPTH=1) — 现象分析
│   ├── Worker: 性能指标趋势分析（响应时间/吞吐量/错误率）
│   └── Worker: 用户反馈收集与分类
├── 循环 2：Adaptor-B (DEPTH=1) — 根因定位
│   ├── Worker: 资源使用分析（CPU/内存/磁盘/网络）
│   └── Worker: 慢查询/慢请求分析
└── 循环 3：Worker — 综合诊断报告
```

### 核心要点

- **现象先行**：先确认"变慢"的具体表现
- **资源关联**：性能变化通常与资源瓶颈相关
- **根因定位**：找到根本原因，而非症状
- **验证链穿透**：每层诊断都有数据支撑

### 深度临界点

分析返回"数据库连接池满"。浅答系统建议增加连接池。
本系统继续追问："什么导致连接被长时间占用？"发现真正的根因。

**阶段2：根因定位（复用 Worker-A）**

```

  2. 根因假设验证

Task(

  task_id: "之前返回的 task_id",  // 复用

```

**Worker-A 复用后返回**：

```
**起点**: 基于连接池分析，深入查看慢查询日志
**转折**: 发现 session 写入操作平均耗时 3s，远超正常值
**验证**: 检查 session 写入代码，发现未加锁导致并发竞争

## 执行结果
根因：session 写入未加锁，高并发时连接被长时间占用
影响：连接池耗尽，所有请求排队
...

## 完成状态
已完成(PASS)

## 备注

```

**父级最终验证**：
```
## 结论挑战响应
Q: 增加连接池大小能否解决问题？
A: 不能。根因是 session 写入未加锁导致竞争，增加连接池只是治标不治本。

Q: 为什么之前没有发现这个问题？
A: 用户量增长导致并发增加，之前并发量不足以触发问题。
```

**最终结论**：session 写入未加锁是根本原因，而非连接池配置不足。

## DEPTH 3：架构问题识别

> 用户：系统越来越难维护了，帮我分析一下问题

### 树结构

```
L1 Adaptor (DEPTH=3)
├── 循环 1：Adaptor-A (DEPTH=2) — 代码层分析
│   ├── Adaptor (DEPTH=1) — 结构分析
│   │   ├── Worker: 模块耦合度分析
│   │   └── Worker: 循环依赖检测
│   └── Worker: 代码复杂度分析（圈复杂度/认知复杂度）
├── 循环 2：Adaptor-B (DEPTH=2) — 演进分析
│   ├── Adaptor (DEPTH=1) — 变更分析
│   │   ├── Worker: 热点文件识别（频繁修改）
│   │   └── Worker: 变更影响范围分析
│   └── Worker: 技术债务识别与评估
└── 循环 3：Adaptor-C (DEPTH=1) — 综合诊断
    ├── Worker: 问题优先级排序
    └── Worker: 改进建议与路线图
```

### 核心要点

- **多维度分析**：结构 + 复杂度 + 演进历史
- **量化指标**：用数据说话，而非主观判断
- **可操作性**：给出优先级和改进路线

### 深度临界点

DEPTH=2 可能只分析代码结构。DEPTH=3 多了演进分析（热点文件、变更影响），发现维护难的真正原因。

## DEPTH 4：用户流失分析

> 用户：上个月留存率下降 5%，帮我找原因

### 树结构

```
L1 Adaptor (DEPTH=4)
├── 循环 1：Adaptor-A (DEPTH=3) — 数据可信度验证
│   ├── Adaptor (DEPTH=2) — 统计口径核查
│   │   ├── Adaptor (DEPTH=1) — 原始数据溯源
│   │   │   ├── Worker: 拉取原始事件日志，手工验算留存率
│   │   │   └── Worker: 核查统计脚本版本变更记录
│   │   └── Worker: 与第三方埋点平台数据对比
│   └── Adaptor (DEPTH=1) — 历史基线验证
│       ├── Worker: 过去 6 个月留存率趋势一致性
│       └── Worker: 同期行业基准数据对比
├── 循环 2：Adaptor-B (DEPTH=3) — 真实下降归因
│   ├── Adaptor (DEPTH=2) — 分层分析
│   │   ├── Adaptor (DEPTH=1) — 用户分群
│   │   │   ├── Worker: 按来源/时段/设备/地区拆分留存
│   │   │   └── Worker: 新用户 vs 老用户留存差异
│   │   └── Worker: 最显著下降用户群的行为路径分析
│   └── Adaptor (DEPTH=1) — 产品变更归因
│       ├── Worker: 该时期产品变更记录（功能/UI/实验）
│       └── Worker: 变更时间轴 vs 留存下降时间轴对比
└── 循环 3：Worker — 综合归因报告
```

### 核心要点

- **数据验证先行**：5% 下降可能包含统计口径变化
- **分层定位**：从整体到细分，找到问题集中点
- **因果验证**：时间轴对比 + AB 实验验证
- **结论挑战**：AB 实验存在选择偏差，需要控制变量重新分析

### 深度临界点

DEPTH=3 可能在 AB 数据证实"改版组留存更低"后接受结论。
DEPTH=4 发现 AB 实验存在选择偏差（按注册时间而非随机 ID 分配），将影响量级从 3% 修正为 1.8%，并识别出并行根因。

- 多源验证（避免单一信息源偏差）

## 向下拓展方法

DEPTH > 5 的发现型任务，按以下模式拓展：

### 1. 观察范围拓宽
- DEPTH +1：增加更多数据源
- DEPTH +2：增加定性研究（访谈/调研）
- DEPTH +3：增加外部对标（竞争对手/行业标杆）

### 2. 分析框架加深
- DEPTH +1：增加分析维度
- DEPTH +2：增加时间维度（趋势分析）
- DEPTH +3：增加空间维度（对比分析）

### 3. 验证方式加严
- DEPTH +1：增加交叉验证
- DEPTH +2：增加专家评审
- DEPTH +3：增加小范围试点验证

### 4. 洞察深度加强
- DEPTH +1：从现象到原因
- DEPTH +2：从原因到根因
- DEPTH +3：从根因到可行动建议

### 拓展原则

- **发现型任务的核心是定义问题**
- **每增加一层，应发现一个新的洞察**
- **最终输出应能回答"这为什么重要"和"我们该怎么做"**
- **每个诊断结论都必须有结论挑战验证**

### 验证类型递进

| 层级 | 验证类型 | 示例 |
|------|----------|------|
| L1-L2 | 检查清单 + 结构化输出 | 数据来源标注 + 格式完整 |
| L3-L4 | 交叉验证 + 结论挑战 | 多源对比 + 反驳验证 |
| L5+ | 专家评审 + 试点验证 | 第三方验证 + 实际环境测试 |
