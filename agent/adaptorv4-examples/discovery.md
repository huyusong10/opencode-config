# 发现型任务样例

## 类型定义

**特征**：目标不明确 + 需要先定义问题 + 发现模式/机会

**OODA重点**：Observe + Orient（观察与定向）

**场景**：业务分析、数据挖掘、问题发现、机会识别

**起点**：初步摸底 → 确定分析框架 → 并行各维度深度调研 → 完整性检查 → 综合

---

## 深度临界点判断

| DEPTH | 侧重点 | 深度临界点 |
|-------|--------|------------|
| 1-2 | 模式识别 | 识别分布和变化，而非单点 |
| 3 | 归因 | 多维度量化分析 |
| 4 | 验证 | 数据可信度 + 交叉验证 |
| 5+ | 战略 | 外部对标 + 多源验证 |

**浅答基线**：列出错误。本系统识别异常模式（新出现的/频率突增的）；深入时发现根因而非症状。

## 经验传递示例（DEPTH 2）

### 任务

> 系统最近变慢了，不知道为什么

### 树结构

```
L1 Adaptor (DEPTH=2)
├── 循环 1：Adaptor-A (DEPTH=1) — 现象分析
│   ├── Worker: 性能指标趋势分析
│   └── Worker: 用户反馈收集与分类
├── 循环 2：Adaptor-B (DEPTH=1) — 根因定位
│   ├── Worker: 资源使用分析
│   └── Worker: 慢查询/慢请求分析
└── 循环 3：Worker — 综合诊断报告
```

### 阶段1：现象分析

**委托**：
```markdown
[目标-验证声明]
目标: 分析系统变慢的现象和瓶颈指标
验证类型: 检查清单 + 结构化输出
验证方式: 性能指标有来源 + 用户反馈有时间分布
PASS条件: 三项验证通过

温度策略 temperature=0.2 | 理由：数据分析任务，需数据准确性
```

**Worker 返回关键发现**：
- P99 从 200ms 升至 5s
- 连接池使用率持续 100%
- 投诉集中在 10:00-12:00 业务高峰

### 阶段2：根因定位（复用 Worker）

**注入共享上下文**：
```markdown
[共享上下文 - 来自阶段1]
- 瓶颈: 数据库连接池耗尽
- 高发时段: 10:00-12:00 业务高峰

深入分析：
- 哪些 SQL 占用连接时间最长
- 是否存在慢查询或连接泄漏
```

**Worker 返回**：
- session 写入操作平均耗时 3s，远超正常值
- 根因：session 写入未加锁，高并发时连接被长时间占用

### 父级结论挑战

```
Q: 增加连接池大小能否解决问题？
A: 不能。根因是 session 写入未加锁导致竞争，增加连接池治标不治本。

Q: 为什么之前没有发现这个问题？
A: 用户量增长导致并发增加，之前并发量不足以触发问题。
```

**最终结论**：session 写入未加锁是根本原因，而非连接池配置不足。

## DEPTH 3：架构问题识别

> 系统越来越难维护了，帮我分析一下问题

```
L1 Adaptor (DEPTH=3)
├── 循环 1：Adaptor-A (DEPTH=2) — 代码层分析
│   ├── Adaptor (DEPTH=1) — 结构分析
│   │   ├── Worker: 模块耦合度分析
│   │   └── Worker: 循环依赖检测
│   └── Worker: 代码复杂度分析
```

## DEPTH 4：用户流失分析

> 上个月留存率下降 5%，帮我找原因

```
L1 Adaptor (DEPTH=4)
├── 循环 1：Adaptor-A (DEPTH=3) — 数据可信度验证
│   ├── Adaptor (DEPTH=2) — 统计口径核查
│   │   ├── Adaptor (DEPTH=1) — 原始数据溯源
│   │   │   ├── Worker: 拉取原始事件日志，手工验算
│   │   │   └── Worker: 核查统计脚本版本变更
│   │   └── Worker: 与第三方埋点平台数据对比
│   └── Adaptor (DEPTH=1) — 历史基线验证
│       ├── Worker: 过去 6 个月留存率趋势
│       └── Worker: 同期行业基准对比
├── 循环 2：Adaptor-B (DEPTH=3) — 真实下降归因
│   ├── Adaptor (DEPTH=2) — 分层分析
│   │   ├── Adaptor (DEPTH=1) — 用户分群
│   │   │   ├── Worker: 按来源/时段/设备/地区拆分
│   │   │   └── Worker: 新用户 vs 老用户留存差异
│   │   └── Worker: 最显著下降用户群的行为路径
│   └── Adaptor (DEPTH=1) — 产品变更归因
│       ├── Worker: 该时期产品变更记录
│       └── Worker: 变更时间轴 vs 留存下降时间轴
└── 循环 3：Worker — 综合归因报告
```

**核心要点**：数据验证先行；分层定位；因果验证；结论挑战

**临界点**：DEPTH=3 可能在 AB 数据证实后接受结论。DEPTH=4 发现 AB 实验存在选择偏差，修正影响量级，识别并行根因。

## 向下拓展方法

DEPTH > 5 按以下模式拓展：

### 拓展方向

| 维度 | DEPTH +1 | DEPTH +2 | DEPTH +3 |
|------|----------|----------|----------|
| 观察范围 | 更多数据源 | 定性研究（访谈/调研）| 外部对标 |
| 分析框架 | 增加分析维度 | 时间维度（趋势）| 空间维度（对比）|
| 验证方式 | 交叉验证 | 专家评审 | 小范围试点 |
| 洞察深度 | 现象→原因 | 原因→根因 | 根因→可行动建议 |

### 拓展原则

- 发现型任务的核心是定义问题
- 每增加一层，应发现一个新的洞察
- 最终输出应能回答"这为什么重要"和"我们该怎么做"

### 验证类型递进

| 层级 | 验证类型 |
|------|----------|
| L1-L2 | 检查清单 + 结构化输出 |
| L3-L4 | 交叉验证 + 结论挑战 |
| L5+ | 专家评审 + 试点验证 |
