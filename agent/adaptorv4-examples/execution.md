# 执行型任务样例

## 类型定义

**特征**：目标明确 + 路径明确 + 有验收标准

**OODA重点**：Act（执行）

**场景**：功能实现、代码修复、配置部署、数据迁移

**起点**：调研 → 接口设计 → 并行（实现 + 测试代码）→ 验证

---

## 深度临界点判断

| DEPTH | 侧重点 | 深度临界点 |
|-------|--------|------------|
| 1-2 | 实现 | 调研现有规范，确保风格一致 |
| 3 | 设计 | 多方案对比 + 风险评估 |
| 4 | 架构 | 依赖分析 + 隐式状态识别 |
| 5+ | 验证 | 混沌测试 + 边界条件覆盖 |

**浅答基线**：直接写代码。本系统先调研现有规范，确保风格一致；深入时发现隐式依赖和边界情况。

## 经验传递示例（DEPTH 2）

### 任务

> 管理员需要能把用户列表导出成 CSV

### 树结构

```
L1 Adaptor (DEPTH=2)
├── 循环 1：Adaptor-A (DEPTH=1) — 系统调研
│   ├── Worker: 用户规模 + 权限系统
│   └── Worker: 现有 API 规范
├── 循环 2：Worker — 接口设计
├── 循环 3：Adaptor-B (DEPTH=1) — 后端实现
│   ├── Worker: 实现导出逻辑
│   └── Worker: 编写验收测试
└── 循环 4：Worker — 运行测试套件
```

### 阶段1：系统调研

**委托**：
```markdown
[目标-验证声明]
目标: 调研用户规模和现有 API 规范
验证类型: 结构化输出
验证方式: 用户规模数据 + API 规范文档
PASS条件: 两项数据完整且有来源

温度策略 temperature=0.2 | 理由：调研类任务，需数据准确性
```

**Worker 返回关键发现**：
- 用户规模：50 万，月增长 2 万
- HTTP 超时：30s，同步导出不可行

### 阶段2：接口设计（方向调整）

**父级提取并注入共享上下文**：
```markdown
[共享上下文 - 来自阶段1]
- 用户规模: 50 万，同步导出会超时
- HTTP 超时: 30s

任务：设计异步导出 API
```

**Worker 返回**：
- API 设计：POST 创建任务 → GET 查询状态 → GET 下载
- 并发限制：每管理员最多 1 个进行中任务

### 父级结论挑战

```
Q: 如果任务创建后用户关闭页面，如何通知用户任务完成？
A: 可随时查询状态。后续可增加邮件/站内信通知。

Q: 24小时过期时间是否合理？
A: 可根据实际文件大小测试后调整。
```

## DEPTH 3：权限系统实现

> 给系统添加基于角色的权限控制，支持多租户

```
L1 Adaptor (DEPTH=3)
├── 循环 1：Adaptor-A (DEPTH=2) — 现有系统调研
│   ├── Adaptor (DEPTH=1) — 数据层分析
│   │   ├── Worker: 用户/租户数据模型
│   │   └── Worker: 权限检查点分布
│   └── Worker: 认证中间件分析
├── 循环 2：Adaptor-B (DEPTH=2) — 设计与实现
│   ├── Adaptor (DEPTH=1) — 数据模型设计
│   │   ├── Worker: RBAC 模型设计
│   │   └── Worker: 多租户隔离方案
│   └── Adaptor (DEPTH=1) — 代码实现
│       ├── Worker: 权限中间件
│       └── Worker: 权限管理 API
└── 循环 3：Adaptor-C (DEPTH=1) — 测试与迁移
    ├── Worker: 权限测试套件
    └── Worker: 现有代码权限接入
```

**核心要点**：分层调研（数据层+认证层+权限检查点）；并行设计（RBAC+多租户）

**临界点**：DEPTH=2 可能只做权限中间件。DEPTH=3 多了现有权限检查点分析 + 迁移方案。

## DEPTH 4：微服务模块实现

> 实现订单服务的微服务拆分，从单体中独立部署

```
L1 Adaptor (DEPTH=4)
├── 循环 1：Adaptor-A (DEPTH=3) — 现有订单模块分析
│   ├── Adaptor (DEPTH=2) — 代码依赖分析
│   │   ├── Adaptor (DEPTH=1) — 静态依赖
│   │   │   ├── Worker: 模块间调用关系图谱
│   │   │   └── Worker: 数据库表归属分析
│   │   └── Worker: 共享状态识别
│   └── Adaptor (DEPTH=1) — 接口契约分析
│       ├── Worker: 现有 API 契约
│       └── Worker: 内部服务调用契约
├── 循环 2：Adaptor-B (DEPTH=3) — 服务边界设计
│   ├── Adaptor (DEPTH=2) — 接口设计
│   │   ├── Adaptor (DEPTH=1) — 对外接口
│   │   │   ├── Worker: REST API 设计
│   │   │   └── Worker: 事件契约设计
│   │   └── Worker: 内部服务接口
│   └── Adaptor (DEPTH=1) — 数据层设计
│       ├── Worker: 数据库拆分方案
│       └── Worker: 缓存策略
├── 循环 3：Adaptor-C (DEPTH=2) — 核心实现
│   ├── Adaptor (DEPTH=1) — 业务逻辑
│   │   ├── Worker: 订单核心逻辑迁移
│   │   └── Worker: 事件发布实现
│   └── Adaptor (DEPTH=1) — 基础设施
│       ├── Worker: 数据访问层
│       └── Worker: 服务注册与发现
└── 循环 4：Adaptor-D (DEPTH=1) — 测试与部署
    ├── Worker: 集成测试套件
    └── Worker: CI/CD 配置
```

**核心要点**：依赖深度分析（跨模块调用+共享状态+数据库耦合）；接口先行

**临界点**：DEPTH=3 可能遗漏共享状态分析。DEPTH=4 深入到代码级依赖，发现隐式共享状态（全局变量、静态缓存）。

## 向下拓展方法

DEPTH > 5 按以下模式拓展：

### 拓展方向

| 维度 | DEPTH +1 | DEPTH +2 | DEPTH +3 |
|------|----------|----------|----------|
| 调研 | 竞品分析 | POC 验证 | 性能基准测试 |
| 设计 | 备选方案对比 | 风险分析与缓解 | 可扩展性设计 |
| 实现 | 代码审查 | 性能优化迭代 | 安全审计 |
| 验证 | 边界条件测试 | 压力测试/混沌测试 | 灰度发布验证 |

### 拓展原则

- 每增加一层，至少有一个独立验证维度
- 不是所有子任务都需要最大深度，按需分配
- 新层级应有明确的验收条件

### 验证类型递进

| 层级 | 验证类型 |
|------|----------|
| L1-L2 | 脚本验证 |
| L3-L4 | 检查清单 + 结构化输出 |
| L5+ | 结论挑战 + 混沌测试 |
