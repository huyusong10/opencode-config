# 执行型任务样例

## 类型定义

**特征**：目标明确 + 路径明确 + 有验收标准

**OODA重点**：Act（执行）

**典型场景**：功能实现、代码修复、配置部署、数据迁移

**默认起点结构**：调研 → 接口设计 → 并行（实现 + 测试代码）→ 验证

---

## DEPTH 1：添加 API 端点

> 用户：给用户服务添加一个 `/api/users/{id}/profile` 的 GET 接口

### 树结构

```
L1 Adaptor (DEPTH=1)
├── Worker: 调研现有用户服务代码结构和 API 规范
└── Worker: 实现接口 + 编写单元测试
```

### 核心要点

- **单层执行**：任务简单，直接派 Worker
- **调研先行**：即使是简单任务，也先了解现有结构
- **验收明确**：接口返回正确、测试通过

### 深度临界点

浅答系统直接写代码。本系统先调研现有 API 规范，确保新接口风格一致。

## DEPTH 2：新增用户 CSV 导出

> 用户：管理员需要能把用户列表导出成 CSV

### 树结构

```
L1 Adaptor (DEPTH=2)
├── 循环 1：Adaptor-A (DEPTH=1) — 系统调研
│   ├── Worker: 现有用户数据结构 + 权限系统 + 用户规模
│   └── Worker: 现有 API 规范 + 类似导出功能
├── 循环 2：Worker — 接口设计
├── 循环 3：Adaptor-B (DEPTH=1) — 后端实现
│   ├── Worker: 实现导出逻辑
│   └── Worker: 编写验收测试代码
└── 循环 4：Worker — 运行测试套件
```

### 核心要点

- **规模驱动设计**：用户规模决定同步/异步方案
- **结论挑战**：50 万用户下，同步导出会超时，需改为异步
- **多轮迭代**：调研 → 设计 → 实现 → 验证

### 深度临界点

接口设计交付 `GET /api/export/users`。浅答系统接受。本系统挑战："50万用户下会超时"，重委托要求异步方案。

### 经验传递示例

以下是本样例中经验传递的具体过程：

**阶段1：系统调研**

Worker-A（用户规模调研）返回：
```
## 研究路径
**起点**: 搜索用户数据库，统计用户总数
**转折**: 发现用户数已达 50 万，且每月新增约 2 万
**验证**: 对比去年同期数据，确认增长趋势

## 执行结果
用户规模：50 万，月增长 2 万
预估导出数据量：50 万行 CSV，约 100MB
...

## 完成状态
已完成
```

Worker-B（API 规范调研）返回：
```
## 研究路径
**起点**: 搜索现有 API 代码，了解接口风格
**转折**: 发现现有 HTTP 超时配置为 30s
**验证**: 确认 100MB CSV 生成 + 传输无法在 30s 内完成

## 执行结果
HTTP 超时限制：30s
同步导出不可行，需要异步方案
...

## 完成状态
已完成
```

**父级提取关键发现**：
- 用户规模 50 万，同步导出会超时
- HTTP 超时 30s，需要异步方案

**阶段2：接口设计（基于发现调整方向）**

父级调整方案后委托设计：
```
Task(
  subagent_type: "adaptorv4-worker",
  prompt: """
[共享上下文 - 来自阶段1]
- 用户规模: 50 万，同步导出会超时
- HTTP 超时: 30s

任务：设计异步导出 API
- 创建任务 → 查询状态 → 下载文件
- 考虑并发限制和任务过期
"""
)
```

**Worker 设计后返回**：
```
## 研究路径
**起点**: 基于规模约束，设计异步任务模式
**转折**: 发现需要考虑并发限制，避免多管理员同时导出导致服务器过载
**验证**: 参考 AWS 导出 API 设计，确认模式可行

## 执行结果
API 设计：POST 创建任务 → GET 查询状态 → GET 下载
并发限制：每管理员最多 1 个进行中任务
任务过期：24 小时
...

## 完成状态
已完成
```

## DEPTH 3：权限系统实现

> 用户：给系统添加基于角色的权限控制，支持多租户

### 树结构

```
L1 Adaptor (DEPTH=3)
├── 循环 1：Adaptor-A (DEPTH=2) — 现有系统调研
│   ├── Adaptor (DEPTH=1) — 数据层分析
│   │   ├── Worker: 现有用户/租户数据模型
│   │   └── Worker: 现有权限检查点分布
│   └── Worker: 现有认证中间件分析
├── 循环 2：Adaptor-B (DEPTH=2) — 设计与实现
│   ├── Adaptor (DEPTH=1) — 数据模型设计
│   │   ├── Worker: RBAC 模型设计
│   │   └── Worker: 多租户隔离方案设计
│   └── Adaptor (DEPTH=1) — 代码实现
│       ├── Worker: 权限中间件实现
│       └── Worker: 权限管理 API 实现
└── 循环 3：Adaptor-C (DEPTH=1) — 测试与迁移
    ├── Worker: 权限测试套件编写
    └── Worker: 现有代码权限接入迁移
```

### 核心要点

- **分层调研**：数据层 + 认证层 + 权限检查点
- **并行设计**：RBAC 模型 + 多租户隔离可并行
- **迁移风险**：现有代码接入需要全面回归

### 深度临界点

DEPTH=2 可能只做权限中间件。DEPTH=3 多了现有权限检查点分析 + 迁移方案，避免遗漏。

## DEPTH 4：微服务模块实现

> 用户：实现订单服务的微服务拆分，从单体中独立部署

### 树结构

```
L1 Adaptor (DEPTH=4)
├── 循环 1：Adaptor-A (DEPTH=3) — 现有订单模块分析
│   ├── Adaptor (DEPTH=2) — 代码依赖分析
│   │   ├── Adaptor (DEPTH=1) — 静态依赖
│   │   │   ├── Worker: 模块间调用关系图谱
│   │   │   └── Worker: 数据库表归属分析
│   │   └── Worker: 共享状态识别
│   └── Adaptor (DEPTH=1) — 接口契约分析
│       ├── Worker: 现有 API 契约梳理
│       └── Worker: 内部服务调用契约
├── 循环 2：Adaptor-B (DEPTH=3) — 服务边界设计
│   ├── Adaptor (DEPTH=2) — 接口设计
│   │   ├── Adaptor (DEPTH=1) — 对外接口
│   │   │   ├── Worker: REST API 设计
│   │   │   └── Worker: 事件契约设计
│   │   └── Worker: 内部服务接口
│   └── Adaptor (DEPTH=1) — 数据层设计
│       ├── Worker: 数据库拆分方案
│       └── Worker: 缓存策略设计
├── 循环 3：Adaptor-C (DEPTH=2) — 核心实现
│   ├── Adaptor (DEPTH=1) — 业务逻辑
│   │   ├── Worker: 订单核心逻辑迁移
│   │   └── Worker: 事件发布实现
│   └── Adaptor (DEPTH=1) — 基础设施
│       ├── Worker: 数据访问层实现
│       └── Worker: 服务注册与发现
└── 循环 4：Adaptor-D (DEPTH=1) — 测试与部署
    ├── Worker: 集成测试套件
    └── Worker: CI/CD 配置
```

### 核心要点

- **依赖深度分析**：跨模块调用 + 共享状态 + 数据库耦合
- **接口先行**：先设计契约，再实现
- **渐进迁移**：核心逻辑 → 基础设施 → 测试部署

### 深度临界点

DEPTH=3 可能遗漏共享状态分析。DEPTH=4 深入到代码级依赖，发现隐式共享状态（如全局变量、静态缓存），这些是服务拆分的关键障碍。

## DEPTH 5：分布式事务系统

> 用户：实现支持 SAGA 模式的分布式事务协调器

### 树结构

```
L1 Adaptor (DEPTH=5)
├── 循环 1：Adaptor-A (DEPTH=4) — 需求与架构
│   ├── Adaptor (DEPTH=3) — 业务场景分析
│   │   ├── Adaptor (DEPTH=2) — 现有事务场景
│   │   │   ├── Adaptor (DEPTH=1) — 跨服务事务识别
│   │   │   │   ├── Worker: 现有跨服务调用链分析
│   │   │   │   └── Worker: 一致性需求分类
│   │   │   └── Worker: 失败场景枚举
│   │   └── Adaptor (DEPTH=1) — SAGA 模式适配分析
│   │       ├── Worker: 补偿逻辑可行性评估
│   │       └── Worker: 幂等性现状分析
│   └── Adaptor (DEPTH=2) — 技术选型
│       ├── Adaptor (DEPTH=1) — 竞品分析
│       │   ├── Worker: 开源方案对比（Seata/Saga/DTM）
│       │   └── Worker: 自研 vs 集成评估
│       └── Worker: 存储选型（DB vs 消息队列）
├── 循环 2：Adaptor-B (DEPTH=4) — 核心设计
│   ├── Adaptor (DEPTH=3) — 状态机设计
│   │   ├── Adaptor (DEPTH=2) — 状态模型
│   │   │   ├── Adaptor (DEPTH=1) — 状态定义
│   │   │   │   ├── Worker: 事务状态枚举
│   │   │   │   └── Worker: 状态转换规则
│   │   │   └── Worker: 持久化模型
│   │   └── Adaptor (DEPTH=1) — 补偿策略
│   │       ├── Worker: 补偿动作编排
│   │       └── Worker: 超时与重试策略
│   └── Adaptor (DEPTH=2) — 协调器设计
│       ├── Adaptor (DEPTH=1) — 核心组件
│       │   ├── Worker: 协调器核心逻辑
│       │   └── Worker: 事务日志管理
│       └── Worker: 恢复机制设计
├── 循环 3：Adaptor-C (DEPTH=3) — 实现
│   ├── Adaptor (DEPTH=2) — 核心实现
│   │   ├── Adaptor (DEPTH=1) — 协调器
│   │   │   ├── Worker: SAGA 协调器实现
│   │   │   └── Worker: 事务上下文管理
│   │   └── Worker: 补偿执行器
│   └── Adaptor (DEPTH=1) — SDK 实现
│       ├── Worker: 客户端 SDK
│       └── Worker: 注解/装饰器支持
└── 循环 4：Adaptor-D (DEPTH=2) — 测试与集成
    ├── Adaptor (DEPTH=1) — 测试
    │   ├── Worker: 单元测试
    │   └── Worker: 混沌测试（网络分区/进程崩溃）
    └── Adaptor (DEPTH=1) — 集成
        ├── Worker: 业务服务接入示例
        └── Worker: 监控与告警配置
```

### 核心要点

- **场景驱动**：从现有跨服务事务场景出发，而非先设计架构
- **失败优先**：先枚举失败场景，再设计补偿策略
- **混沌验证**：分布式系统必须测试网络分区、进程崩溃等故障

### 深度临界点

DEPTH=4 可能只实现核心协调器。DEPTH=5 多了：
- 幂等性现状分析（决定 SAGA 是否可行）
- 混沌测试（验证分布式场景下的正确性）
- 业务服务接入示例（确保可用性）

## 向下拓展方法

DEPTH > 5 的执行型任务，按以下模式拓展：

### 1. 调研层加深
- DEPTH +1：增加竞品分析（同类系统/开源方案）
- DEPTH +2：增加 POC 验证（关键技术的原型验证）
- DEPTH +3：增加性能基准测试

### 2. 设计层加深
- DEPTH +1：增加备选方案对比
- DEPTH +2：增加风险分析与缓解策略
- DEPTH +3：增加可扩展性设计

### 3. 实现层加深
- DEPTH +1：增加代码审查环节
- DEPTH +2：增加性能优化迭代
- DEPTH +3：增加安全审计

### 4. 验证层加深
- DEPTH +1：增加边界条件测试
- DEPTH +2：增加压力测试/混沌测试
- DEPTH +3：增加灰度发布验证

### 拓展原则

- **每增加一层，至少有一个独立验证维度**
- **不是所有子任务都需要最大深度，按需分配**
- **新层级应有明确的验收条件，不能无限嵌套**
