# 复合型任务样例

## 类型定义

**特征**：涉及多种类型（执行/探索/发现）+ 需要分阶段处理 + 阶段间有依赖

**OODA重点**：全流程协调

**场景**：调研+修复、评估+决策、分析+方案、端到端改造

**起点**：按类型分解 → 确定阶段依赖 → 分阶段执行

---

## 复合型识别

满足以下之一即为复合型：

| 条件 | 示例 |
|------|------|
| 跨类型输出 | "分析问题 + 给出方案" |
| 工具链切换 | 调研（探索型）+ 实现（执行型）|
| 角色转换 | 分析师 + 工程师 |
| 阶段依赖 | 后续输入依赖前序输出 |

### 常见组合模式

| 组合 | 场景 | 阶段依赖 |
|------|------|----------|
| 发现 + 执行 | 问题定位 + 修复 | 根因确定 → 代码修改 |
| 探索 + 执行 | 技术选型 + 实现 | 方案确定 → 开始实现 |
| 发现 + 探索 + 执行 | 业务分析 + 架构设计 + 实现 | 问题定义 → 方案设计 → 实施 |

---

## 深度临界点判断

| DEPTH | 侧重点 | 深度临界点 |
|-------|--------|------------|
| 2 | 阶段划分 | 探索→执行，依赖明确 |
| 3 | 多阶段协调 | 三阶段闭环 |
| 4 | 深度诊断 | 问题深度定位 |
| 5+ | 全景分析 | 组织因素 + 风险评估 |

**浅答基线**：直接修复或给出方案。本系统先定位根因再修复；深入时发现组织能力和风险因素。

## DEPTH 2：调研 + 修复

### 任务

> 登录时偶尔出现 500 错误，帮我修一下

### Adaptor 视角

#### Observe

- 约束条件：现有登录系统、错误日志
- 知识缺口：错误原因、触发条件
- 验证标准：修复后错误不再出现

#### Orient

- 任务类型：复合型（发现 + 执行）
- 阶段划分：
  - 阶段 1（探索型）：根因调研
  - 阶段 2（执行型）：修复与验证
- **复杂度判断**：中等复杂，需先定位根因
- **委托决策**：调研派 Adaptor，修复派 Adaptor
- **DEPTH 使用**：DEPTH=2，调研 DEPTH=1，修复 DEPTH=1

#### Decide - 循环 1（探索型阶段）

**委托 Adaptor**（根因调研，需日志分析和代码溯源）：
```markdown
[目标-验证声明]
目标: 定位登录 500 错误的根本原因
验证类型: 结论挑战 + 结构化输出
验证方式: 假设有验证路径 + 根因有代码证据
PASS条件: 根因确认，非猜测

温度策略 temperature=0.25 | 理由：根因分析，需严谨逻辑

Task(
  subagent_type: "adaptorv4",
  prompt: """
  DEPTH=1
  
  任务：定位登录 500 错误根因
  
  分析范围：
  1. 错误日志分析，生成假设
  2. 代码溯源，验证假设
  3. 触发路径确认
  
  输出格式：
  - 根因报告
  - 触发条件
  - 影响范围
  """
)
```

#### Act - 循环 1

**Adaptor 返回关键发现**：
- 根因：`sessionStore.Write()` 缺少互斥锁
- 触发路径：高并发登录 → session 写入竞争 → 数据损坏
- 验证脚本：`test_concurrent_session.go`

**注入共享上下文**：
```markdown

- 根因: sessionStore.Write() 未加锁
- 触发路径: 高并发登录 → 竞争 → 数据损坏
- 影响范围: 高并发登录场景
- 验证脚本: test_concurrent_session.go
```

**委托 Adaptor**（修复与验证，需代码修改和测试）：
```markdown
[目标-验证声明]
目标: 修复 session 并发写入问题
验证类型: 脚本验证
验证方式: go test -race ./internal/session/...

温度策略 temperature=0.1 | 理由：代码修复，需高度确定性

Task(
  subagent_type: "adaptorv4",
  prompt: """
  DEPTH=1
  
  [共享上下文 - 来自探索阶段]
  - 根因: sessionStore.Write() 未加锁

```

#### Act - 循环 2

**Adaptor 返回验证汇总表**：

| 子任务 | 目标 | 验证方式 | 结果 |

| Worker-B | 并发测试 | 并发测试 | PASS |

**额外发现**：`Delete()` 也未加锁（范围外）

#### 结论挑战

```
Q: 是否需要同时修复 Delete()？

Q: 修复后性能是否受影响？
A: 读写锁对读操作影响小，写操作需等待，但这是必要的正确性保证。
```

**最终结果**：
- 已修复 `sessionStore.Write()` 并发问题
- 测试通过，验证成功
- 后续建议：单独处理 `Delete()` 并发问题

## 向下拓展方法

DEPTH > 5 按以下模式拓展：

### 拓展方向

| 维度 | DEPTH +1 | DEPTH +2 | DEPTH +3 |
|------|----------|----------|----------|
| 阶段拆分 | 每个阶段内部再拆分 | 增加过渡阶段（试点）| 增加验证阶段（复盘）|
| 维度拓展 | 增加业务维度 | 增加组织维度 | 增加生态维度 |
| 深度加深 | 每个子阶段增加验证 | 每个子阶段增加备选方案 | 每个子阶段增加风险缓解 |
| 广度拓宽 | 增加并行阶段 | 增加前置阶段（能力建设）| 增加后续阶段（持续改进）|

### 拓展原则

- 复合型任务的核心是阶段协调
- 每增加一层，应有明确的阶段边界和交付物
- 阶段间依赖关系清晰，避免循环依赖
- 深度分配原则：不确定性高的阶段分配更高深度

### 验证类型递进

| 阶段类型 | 验证类型 |
|----------|----------|
| 发现型阶段 | 检查清单 + 交叉验证 |
| 探索型阶段 | 结论挑战 + 结构化输出 |
| 执行型阶段 | 脚本验证 |
