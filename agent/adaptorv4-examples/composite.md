# 复合型任务样例

## 类型定义

**特征**：涉及多种类型（执行/探索/发现）+ 需要分阶段处理 + 阶段间有依赖

**OODA重点**：全流程协调

**典型场景**：调研+修复、评估+决策、分析+方案、端到端改造

**默认起点结构**：按类型分解 → 确定阶段依赖 → 分阶段执行

---

## 复合类型的识别

当任务满足以下条件之一时，判定为复合型：

1. **跨类型输出**：例如"分析问题 + 给出方案"
2. **工具链切换**：例如"调研（探索型）+ 实现（执行型）"
3. **角色转换**：例如"分析师 + 工程师"
4. **阶段依赖**：后续阶段的输入依赖前序阶段的输出

### 常见组合模式

| 组合 | 典型场景 | 阶段依赖 |
|------|----------|----------|
| 发现 + 探索 | 问题分析 + 方案评估 | 问题定义 → 方案选型 |
| 探索 + 执行 | 技术选型 + 实现 | 方案确定 → 开始实现 |
| 发现 + 执行 | 问题定位 + 修复 | 根因确定 → 代码修改 |
| 发现 + 探索 + 执行 | 业务分析 + 架构设计 + 实现 | 问题定义 → 方案设计 → 实施 |

## DEPTH 2：调研 + 修复

> 用户：登录时偶尔出现 500 错误，帮我修一下

### 树结构

```
L1 Adaptor (DEPTH=2)
├── 循环 1（探索型）：Adaptor-A (DEPTH=1) — 根因调研
│   ├── Worker: 日志分析，生成假设并寻找触发路径
│   └── Worker: 代码溯源，并行验证各假设的代码路径
└── 循环 2（执行型）：Adaptor-B (DEPTH=1) — 修复与验证
    ├── Worker: 实现修复（基于根因报告）
    └── Worker: 运行验收用例
```

### 核心要点

- **阶段划分**：探索阶段（找原因）+ 执行阶段（修问题）
- **依赖关系**：修复依赖根因确定
- **深度分配**：两个阶段各 DEPTH=1，而非一个阶段 DEPTH=2
- **验证链穿透**：探索阶段验证 → 执行阶段验证

### 阶段间路由

```
探索阶段输出 → 执行阶段输入
─────────────────────────────────
根因报告        → 修复方案
验证用例        → 验收标准
假设路径        → 测试场景
验证结果        → 验证方式
```

### 深度临界点

根因调研返回"可能是数据库连接池耗尽"。浅答系统立即调大连接池。
本系统继续追问："什么导致连接被长时间占用？"发现 session 写入未加锁才是根因。

### 经验传递示例

以下是本样例中经验传递的具体过程：

**阶段1：根因调研（探索型）**

父级 Adaptor 委托：
```
[目标-验证声明]
目标: 定位登录 500 错误的根本原因
验证类型: 结论挑战 + 结构化输出
验证方式:
  1. 假设有验证路径
  2. 根因有代码证据
  3. 可复现
PASS条件: 根因确认，非猜测

温度策略 temperature=0.25 | 理由：根因分析，需要严谨逻辑

并行委托：
- Worker-A: 日志分析 | 检查清单验证
- Worker-B: 代码溯源 | 结论挑战验证
```

Worker-A（日志分析）返回：
```
## 验证执行
验证类型: 检查清单
验证方式: 时间聚类 + 路径分析
验证结果: PASS

## 研究路径
**起点**: 搜索登录相关错误日志，按时间聚类
**转折**: 发现 500 错误集中在高并发时段，且与 session 写入相关
**验证**: 对比正常时段日志，确认 session 写入是关键路径

## 执行结果
假设：高并发下 session 并发写入导致竞争条件
触发路径：登录 → session 写入 → 偶发超时
...

## 完成状态
已完成(PASS)
```

Worker-B（代码溯源）返回：
```
## 验证执行
验证类型: 结论挑战
验证方式: 代码分析 + 复现脚本
验证结果: PASS
```
结论挑战响应：
Q: 是否可能是网络问题？
A: 不是。错误集中在 session 写入，网络错误会有不同日志模式。
```

## 研究路径
**起点**: 检查 session 管理代码，查找并发处理逻辑
**转折**: 发现 `sessionStore.Write()` 未加锁，多协程同时写入会覆盖数据
**验证**: 编写复现脚本，确认并发写入可触发数据损坏

## 执行结果
根因确认：`sessionStore.Write()` 缺少互斥锁
影响范围：高并发登录场景
...

## 完成状态
已完成(PASS)
```

**父级验证汇总**：
```

| 子任务 | 目标 | 验证方式 | 结果 |
|--------|------|----------|------|
| Worker-A | 日志分析 | 检查清单 | PASS |
| Worker-B | 代码溯源 | 结论挑战 | PASS |

## 覆盖情况
- [x] 假设生成 - 已验证
- [x] 代码证据 - 已验证
- [x] 复现脚本 - 已验证

## 整合结果
根因确认：session 写入未加锁 → 需添加互斥锁
```

**父级提取关键发现**：
- 根因：session 写入未加锁
- 影响范围：高并发登录
- 修复方向：添加互斥锁

**阶段2：修复实施（执行型）**

注入共享上下文后委托修复：
```

目标: 修复 session 并发写入问题
验证类型: 脚本验证
验证方式: go test -race ./internal/session/...
PASS条件: PASS, 无 race detected

Task(
  subagent_type: "adaptorv4-worker",
  prompt: """
[共享上下文 - 来自阶段1]

```

**Worker 修复后返回**：

...

```

**父级最终验证**：
```

|--------|------|----------|------|

## DEPTH 3：分析 + 决策

> 用户：帮我给工程团队制定下季度 OKR，方向是提升系统稳定性

### 树结构

```
L1 Adaptor (DEPTH=3)
├── 循环 1（发现型）：Adaptor-A (DEPTH=2) — 事故根因分析
│   ├── Adaptor (DEPTH=1) — 事故分析
│   │   ├── Worker: 读取事故记录，按根因分类统计
│   │   └── Worker: 识别主要故障模式
│   └── Worker: 痛点验证（数据可信度检查）
├── 循环 2（探索型）：Adaptor-B (DEPTH=1) — 改进方向评估
│   ├── Worker: 各根因的改进方案评估
│   └── Worker: 行业最佳实践对标
└── 循环 3（执行型）：Worker — OKR 制定
```

### 核心要点

- **三阶段流程**：发现 → 探索 → 执行
- **数据驱动**：OKR 来自事故分析，而非拍脑袋
- **可行性验证**：改进方向需要评估可行性

### 阶段间路由

```
发现阶段输出    → 探索阶段输入 → 执行阶段输入
─────────────────────────────────────────────
根因分类        → 方案评估范围   → OKR 目标来源
痛点优先级      → 改进重点       → KR 量化依据
```

### 深度临界点

用户给"提升稳定性"方向。浅答系统写 KR："系统可用性达到 99.9%"。
本系统调研事故记录，发现 70% 故障源于无灰度的 schema 变更。产出 KR："建立数据库变更灰度发布流程"。

## DEPTH 4：发现 + 探索 + 执行

> 用户：用户投诉支付流程有问题，分析原因并给出解决方案

### 树结构

```
L1 Adaptor (DEPTH=4)
├── 循环 1（发现型）：Adaptor-A (DEPTH=3) — 问题定义
│   ├── Adaptor (DEPTH=2) — 投诉分析
│   │   ├── Adaptor (DEPTH=1) — 投诉分类
│   │   │   ├── Worker: 投诉内容分类与频率统计
│   │   │   └── Worker: 用户画像分析（谁在投诉）
│   │   └── Worker: 投诉时间分布分析
│   └── Adaptor (DEPTH=1) — 问题定位
│       ├── Worker: 支付流程各环节耗时分析
│       └── Worker: 错误率分布分析
├── 循环 2（探索型）：Adaptor-B (DEPTH=2) — 方案评估
│   ├── Adaptor (DEPTH=1) — 方案生成
│   │   ├── Worker: 候选方案生成
│   │   └── Worker: 方案可行性评估
│   └── Worker: 方案对比与推荐
└── 循环 3（执行型）：Adaptor-C (DEPTH=1) — 方案实施
    ├── Worker: 详细实施计划
    └── Worker: 风险缓解措施
```

### 核心要点

- **完整闭环**：定义问题 → 评估方案 → 实施计划
- **深度递减**：发现阶段最深（需要深入定位），执行阶段最浅（路径已明确）
- **输出完整**：不只是分析报告，还包含可执行的方案

### 阶段间路由

```
发现阶段输出    → 探索阶段输入 → 执行阶段输入
─────────────────────────────────────────────
问题清单        → 方案范围       → 实施重点
优先级排序      → 方案权重       → 执行顺序
根因分析        → 方案依据       → 验收标准
```

### 深度临界点

DEPTH=3 可能只做问题分析 + 方案建议。
DEPTH=4 多了问题深度定位（投诉分类 + 时间分布 + 环节分析），方案更有针对性。

## 向下拓展方法

DEPTH > 5 的复合型任务，按以下模式拓展：

### 1. 阶段拆分
- DEPTH +1：每个阶段内部再拆分
- DEPTH +2：增加过渡阶段（如试点阶段）
- DEPTH +3：增加验证阶段（如复盘阶段）

### 2. 维度拓展
- DEPTH +1：增加业务维度
- DEPTH +2：增加组织维度
- DEPTH +3：增加生态维度

### 3. 深度加深
- DEPTH +1：每个子阶段增加验证环节
- DEPTH +2：每个子阶段增加备选方案
- DEPTH +3：每个子阶段增加风险缓解

### 4. 广度拓宽
- DEPTH +1：增加并行阶段
- DEPTH +2：增加前置阶段（如能力建设）
- DEPTH +3：增加后续阶段（如持续改进）

### 拓展原则

- **复合型任务的核心是阶段协调**
- **每增加一层，应有明确的阶段边界和交付物**
- **阶段间依赖关系清晰，避免循环依赖**
- **深度分配原则：不确定性高的阶段分配更高深度**
- **每个阶段都必须有目标-验证声明**

### 验证类型递进

| 阶段类型 | 验证类型 | 示例 |
|----------|----------|------|
| 发现型阶段 | 检查清单 + 交叉验证 | 数据来源 + 多源对比 |
| 探索型阶段 | 结论挑战 + 结构化输出 | 反驳验证 + 对比表 |
| 执行型阶段 | 脚本验证 | 测试用例 PASS |

## 复合型任务处理清单

处理复合型任务时，在入场评估阶段额外确认：

- [ ] 识别任务包含哪些类型（执行/探索/发现）
- [ ] 确定各阶段的先后顺序和依赖关系
- [ ] 为每个阶段分配适当的深度
- [ ] **为每个阶段定义目标-验证声明**（新增）
- [ ] 明确阶段间的交付物和验收标准
- [ ] 规划阶段间的信息流转方式
- [ ] **规划阶段间的验证链穿透**（新增）
