# 执行型任务样例

## 类型定义

**特征**：目标明确 + 路径明确 + 有验收标准

**OODA重点**：Act（执行）

**场景**：功能实现、代码修复、配置部署、数据迁移

**起点**：调研 → 接口设计 → 并行（实现 + 测试代码）→ 验证

---

## 深度临界点判断

| DEPTH | 侧重点 | 深度临界点 |
|-------|--------|------------|
| 1-2 | 实现 | 调研现有规范，确保风格一致 |
| 3 | 设计 | 多方案对比 + 风险评估 |
| 4 | 架构 | 依赖分析 + 隐式状态识别 |
| 5+ | 验证 | 混沌测试 + 边界条件覆盖 |

**浅答基线**：直接写代码。本系统先调研现有规范，确保风格一致；深入时发现隐式依赖和边界情况。

## DEPTH 1：添加 API 端点

### 任务

> 给用户服务添加一个 `/api/users/{id}/profile` 的 GET 接口

### Adaptor 视角

#### Observe

- 约束条件：现有用户服务、HTTP 框架、API 规范
- 知识缺口：现有代码结构、API 风格、测试覆盖
- 验证标准：接口可用、符合现有规范、有测试

#### Orient

- 任务类型：执行型（目标明确、路径明确）
- **复杂度判断**：预估工具调用 ≤ 10 次，简单任务
- **委托决策**：直接派 Worker，不拆分
- **DEPTH 使用**：DEPTH=1，实际消耗 DEPTH=0

**委托 Worker**（调研先行）：
```markdown

PASS条件: 包含目录结构、认证方式、响应格式、测试模式

温度策略 temperature=0.2 | 理由：调研类任务，需数据准确性

Task(
  subagent_type: "adaptorv4-worker",
  prompt: """
  任务：调研用户服务现状

  1. 用户服务目录结构
```

## 向下拓展方法

DEPTH > 5 按以下模式拓展：

### 拓展方向

| 维度 | DEPTH +1 | DEPTH +2 | DEPTH +3 |
|------|----------|----------|----------|
| 调研 | 竞品分析 | POC 验证 | 性能基准测试 |
| 设计 | 备选方案对比 | 风险分析与缓解 | 可扩展性设计 |
| 实现 | 代码审查 | 性能优化迭代 | 安全审计 |
| 验证 | 边界条件测试 | 压力测试/混沌测试 | 灰度发布验证 |

### 拓展原则

- 每增加一层，至少有一个独立验证维度
- 不是所有子任务都需要最大深度，按需分配
- 新层级应有明确的验收条件

### 验证类型递进

| 层级 | 验证类型 |
|------|----------|
| L1-L2 | 脚本验证 |
| L3-L4 | 检查清单 + 结构化输出 |
| L5+ | 结论挑战 + 混沌测试 |
