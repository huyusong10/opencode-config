# 探索型任务样例

## 类型定义

**特征**：目标明确 + 路径不明确 + 需要对比/评估/设计

**OODA重点**：Orient + Decide（定向与决策）

**场景**：技术选型、架构设计、根因排查、方案评估

**起点**：确定候选范围 → 确定评估维度 → 并行各候选调研 → 对比表 + 推荐

---

## 深度临界点判断

| DEPTH | 侧重点 | 深度临界点 |
|-------|--------|------------|
| 1-2 | 对比 | 搜索最新数据，确保版本准确 |
| 3 | 评估 | 双向案例（成功+失败）|
| 4 | 可行性 | 代码级依赖分析 + 团队能力评估 |
| 5+ | 风险 | 组织因素 + 失败案例研究 |

**浅答基线**：凭记忆回答。本系统搜索最新基准数据，确保版本准确；深入时发现关键约束和迁移成本。

## DEPTH 1：选择 JSON 库

### 任务

> Go 项目选一个 JSON 库，哪个好？

### Adaptor 视角

#### Observe

- 约束条件：Go 项目、现有依赖
- 知识缺口：主流 JSON 库性能数据、功能差异
- 验证标准：有数据支撑的推荐

#### Orient

- 任务类型：探索型（目标明确、路径不明确）
- **复杂度判断**：预估工具调用 ≤ 10 次，简单任务
- **委托决策**：直接并行派 Worker
- **DEPTH 使用**：DEPTH=1，实际消耗 DEPTH=0

#### Decide

**并行委托 Worker**：
```markdown
[目标-验证声明]
目标: 对比 Go 主流 JSON 库，给出推荐
验证类型: 检查清单 + 结构化输出
验证方式: 性能数据有来源 + 功能对比完整
PASS条件: 包含性能、功能、推荐理由

温度策略 temperature=0.2 | 理由：技术对比，需数据准确

并行委托：
- Worker-A: 搜索 Go 主流 JSON 库性能基准测试 | temperature=0.2
- Worker-B: 功能对比（泛型支持/自定义序列化/错误处理）| temperature=0.2
```

#### Act

**Worker-A 返回**：
- 候选：encoding/json、json-iterator、sonic、jsonparser
- 性能：sonic > json-iterator > jsonparser > encoding/json
- 来源：go-json-benchmark GitHub 2024.03

**Worker-B 返回**：
- encoding/json：标准库，稳定，无依赖
- json-iterator：高性能，100% 兼容标准库
- sonic：最快，但需 CGO，特定场景有 bug
- jsonparser：最快解析，但只读不写

#### 结论挑战

```
Q: sonic 最快，为什么不是默认推荐？
A: 需要 CGO，跨平台编译复杂；部分场景有已知 bug。

Q: 性能差异在实际项目中影响多大？
A: 小项目差异可忽略。大项目、高频场景才值得换。
```

**最终推荐**：
- 默认：`encoding/json`（稳定、无依赖）
- 性能敏感：`json-iterator`（兼容性好）
- 极致性能 + 已有 CGO 环境：`sonic`

```markdown
- Worker-A: Kafka vs RabbitMQ 性能基准 | temperature=0.25
- Worker-B: 消息语义差异（死信/优先级支持）| temperature=0.25
```

#### Act - 循环 3

**Worker-A 返回**：
- 性能：Kafka 吞吐量是 RabbitMQ 的 5-10 倍

**Worker-B 返回**（已有）：
- 死信队列：Kafka 需自行实现 DLQ topic
- 优先级：Kafka 不支持，需业务层实现
- 迁移成本：重写 300+ 行业务逻辑

#### 结论挑战

```
Q: 吞吐量优势不能弥补死信队列功能的缺失吗？

Q: 是否可以通过业务层实现 DLQ topic 解决？

Q: 如果未来吞吐量成为瓶颈怎么办？

```

**最终结论**：不支持迁移。当前痛点是死信队列堆积，应优先解决该问题而非更换 MQ。

## 向下拓展方法

DEPTH > 5 按以下模式拓展：

### 拓展方向

| 维度 | DEPTH +1 | DEPTH +2 | DEPTH +3 |
|------|----------|----------|----------|
| 候选范围 | 更多备选方案 | 非主流方案 | 跨领域借鉴 |
| 评估维度 | 成本/风险 | 组织/文化 | 长期演进 |
| 验证方式 | POC 验证 | 小范围试点 | 第三方评审 |
| 决策支持 | 敏感性分析 | 情景规划 | 决策树与概率 |

### 拓展原则

- 探索型任务的核心是降低不确定性
- 每增加一层，应减少一个关键假设
- 最终输出应能回答"为什么选择 A 而不是 B"

### 验证类型递进

| 层级 | 验证类型 |
|------|----------|
| L1-L2 | 检查清单 + 结构化输出 |
| L3-L4 | 结论挑战 |
| L5+ | POC 验证 + 第三方评审 |
