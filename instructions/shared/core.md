# 1. 至高规则

1. 不要假定用户总是正确的；遇到不明确、不合适、与事实或契约冲突的需求，先确认、给建议、征询同意，再执行。详见《2. 需求澄清与同意》。
2. 用户提出每个改进点时，应系统性思考其背后的第一性原理，抽象稳定问题、约束与同类场景，给出最小但完整的系统性方案；若会扩大范围、改变契约或增加风险，必须先征询同意。详见《3. 问题抽象与系统性改进》。
3. 做任何代码修改前，先找到对应的设计文档并理解契约。详见《4. 工作入口》《5. 设计文档原则》。
4. 任何影响对外行为的改动，都必须同步检查并更新 `design/` 与 `tests/`。详见《4. 工作入口》《5. 设计文档原则》《6. 测试原则》。
5. 设计文档、测试用例、AGENTS 规则都不要写得过细、过碎、过度绑定实现。详见《5. 设计文档原则》《6. 测试原则》《8. 动态视角与资产预算》。
6. 完成一个特性后，应主动检查是否存在明显技术债；若存在且风险可控，优先顺手重构。详见《4. 工作入口》。
7. 无论何时都要考虑多语言，不要把特定语言硬编码到代码、测试锚点或契约中。详见《5. 设计文档原则》《6. 测试原则》《7. 多语言原则》。
8. 当前契约、行为验证和历史教训必须形成闭环；历史坑优先转成测试、schema、lint 或当前 design，不能自动化且复发风险高时才写 regression。详见《8. 动态视角与资产预算》。
9. 严格控制 `design/`、`tests/`、历史记录和 AGENTS 规则的膨胀；预算是相对项目规模的约束，超过预算先重构再新增。详见《8. 动态视角与资产预算》。

# 2. 需求澄清与同意

### 目标

- 不把 prompt 当作绝对正确的事实来源；用户可能记错、遗漏上下文，或提出了会伤害长期可维护性的方案。
- 在需求不清或方案不合适时，尽早把风险说清楚，给出更稳的建议，并等待用户同意后再执行。

### 什么时候必须先确认

- 目标、范围、验收标准不明确，继续做会导致大量猜测。
- 用户描述与代码、文档、测试、线上约束或已知事实冲突。
- 用户要求可能破坏对外契约、数据安全、权限边界、隐私、可访问性、多语言能力或核心用户旅程。
- 用户指定的实现方式明显不适合当前代码结构，或存在更低风险、更符合目标的做法。
- 用户要求跳过必要的设计文档、测试、审查、迁移或验证步骤。
- 用户要求执行高成本、破坏性、难回滚或影响面很大的操作。

### 如何确认

- 先用简短语言说明不确定点或风险，不要直接否定用户。
- 给出推荐方案，并说明它为什么更适合当前目标。
- 明确询问用户是否同意推荐方案，或是否仍要按原方案执行。
- 若只是低风险、可逆的小选择，可以说明假设后继续；若会影响契约或用户数据，必须等待明确同意。

### 案例

- 用户说“这个接口没人用，直接改返回结构”：若设计文档或调用方显示它是公开契约，应先说明这是契约变更，建议新增字段或版本化接口，并询问是否同意改为兼容方案。
- 用户要求“把当前中文文案写进测试断言”：应提醒这会把特定语言绑定成契约，建议改用可访问性角色、稳定属性或 `data-testid`，并征询是否按该方式调整。
- 用户要求“删除所有看起来没用的文件”：若无法确认动态引用、构建入口或部署脚本，应先列出候选清单和验证方式，建议先跑搜索与测试，再询问是否继续删除。
- 用户要求“先别管设计文档和测试，直接改功能”：若改动影响对外行为，应说明这违反本文件规则，建议同步更新最小必要设计文档与契约测试，并等待同意。
- 用户说“这个 bug 肯定在前端”：若日志、接口或测试显示问题可能来自后端数据，应说明观察到的证据，建议先定位数据流边界，再确认修复范围。

# 3. 问题抽象与系统性改进

### 目标

- 不只修复用户描述的表面问题，而是识别背后的稳定不变量、系统约束和同类风险。
- 让每个改进点尽可能推动系统变得更一致、更可维护、更不容易在相邻场景再次出错。
- 系统性思考不等于自动扩大实现范围；扩大范围、改变契约、增加迁移成本或引入架构调整前，必须先说明建议并征询用户同意。

### 如何思考

- 先问：用户真正想消除的痛点、风险、约束或不变量是什么？
- 再看：当前问题是否只是一个实例；同类入口、组件、数据结构、状态流或测试锚点是否也有同样风险。
- 方案应优先选择能覆盖同类问题的最小稳定改法，而不是只在单点打补丁。
- 若抽象出了更稳定的规则或契约，应同步检查是否需要更新设计文档和契约测试。
- 若系统性治理会明显超出本次任务，应先列出建议范围、收益和风险，等待用户同意。

### 案例

- 用户说“这个按钮中文太长，改短一点”：不要只改中文文案；应同时考虑多语言、响应式布局、按钮宽度、溢出策略和测试锚点。
- 用户说“这个字段为空会报错”：不要只在一个页面判空；应确认数据入口、schema、默认值、错误语义和同类字段。
- 用户说“这个接口少返回一个字段”：不要只塞字段；应检查接口契约、兼容性、调用方、设计文档和测试。
- 用户说“这里加载太慢，加个 loading”：不要只加 spinner；应先判断问题来自请求时机、缓存、分页、阻塞渲染还是反馈缺失。
- 用户说“这个测试又挂了，改一下断言”：不要只让测试变绿；应判断是测试太脆，还是契约真的被破坏。

# 4. 工作入口

- 修改前先阅读 `design/` 下对应文档；若缺失对应契约，先补最小必要文档，再改代码。
- 优先理解模块职责、公开接口、数据流转、依赖边界，不要先钻内部实现。
- 若改动影响以下任一项，必须在同一次任务中同步更新设计文档与测试：
  - 对外接口
  - 页面路由
  - 核心组件 Props
  - 稳定数据结构
  - 用户主流程
- 若只是内部重构且对外契约不变：
  - 不应为了“配合实现”去改设计文档
  - 不应为了“配合实现”去改契约测试
  - 若原测试因此失败，优先视为契约被破坏
- 完成特性后，主动检查同区域是否存在可顺手治理的技术债，例如超长文件、重复逻辑、脆弱分支、难测模块。

# 5. 设计文档原则

### 目标

- `design/` 是契约说明书，不是实现笔记，不是开发流水账。
- 文档应帮助后来者在不读实现细节的前提下，写出正确调用方或完成安全重构。

### 应写什么

- 模块职责：这个模块存在的唯一理由。
- 对外契约：公开接口、事件、数据结构、错误语义。
- 数据流转：输入 -> 处理边界 -> 输出。
- 依赖边界：依赖谁、期望对方提供什么稳定行为。

### 不要这样写

- 不要把一个稳定能力拆成很多很小的零散文档；优先按模块、页面、接口边界收敛。
- 不要记录内部函数、临时变量、缓存 key、CSS 类名、框架技巧、实现步骤。
- 不要为了“显得完整”把显而易见的实现细节抄进文档。
- 不要把具体中文或英文文案写成契约本身。
- 不要出现“每个组件一个文档、每个小改动一页说明”这类碎片化产物。

### 推荐写法

- 优先用表格、列表、流程图。
- 一份文档只覆盖一个稳定边界；边界过近就合并，边界过大再拆分。
- 文档要短而稳，宁可少写实现，也不要写错契约。

# 6. 测试原则

### 目标

- 测试是重构安全网，首先锁定行为与契约，而不是锁定实现。
- 测试失败必须有意义：要么契约变了，要么行为退化了。

### 分层优先级

- 优先保留少量高价值 E2E，用来锁定核心用户旅程。
- 优先编写接口/集成测试，用来锁定模块边界与数据流。
- 单元测试只用于复杂且稳定的规则、算法或边界条件。

### 不要这样写

- 不要断言私有变量、内部调用顺序、临时状态。
- 不要依赖 CSS 类名、DOM 层级、像素级布局、整页快照。
- 不要把静态文案当成主要断言锚点。
- 不要把一个稳定契约拆成大量细碎、重复、只映射实现分支的小测试。
- 不要为了覆盖率制造大量低价值样板测试。

### 推荐写法

- 断言公开返回值、公开事件、可达路径、稳定结构与错误语义。
- 前端测试优先使用可访问性角色、稳定属性或 `data-testid`。
- UI 样式和静态文案调整通常不应导致契约测试失效。
- 探索用例放在 `tests/scenarios/*.md`，每个核心旅程最多一个，总数尽量少。
- 若改动会让既有契约测试失效，必须明确告知用户这是契约变更，不得静默修改。

# 7. 多语言原则

- 代码、设计文档、测试锚点、数据结构与对外契约都不要默认只有一种语言。
- 不要把具体中文或英文文案当作稳定契约；文案可以变化，语义和结构才是更稳定的边界。
- 前端交互、可访问性名称、测试选择器和错误语义应避免依赖某一种展示语言。
- 新增用户可见内容时，应优先考虑后续接入国际化或替换文案的成本。

# 8. 动态视角与资产预算

### 目标

- `design/` 表达当前稳定契约，`tests/` 验证当前行为，`decisions/` 与 `regressions/` 补足演进视角。
- 历史不是新的真理来源；历史教训必须尽量沉淀为当前契约、自动验证或机器可检查规则。
- 所有规则资产都不是只增不减的仓库；新增内容必须承担维护价值。

### 演进记录怎么用

- 重要架构取舍写入 `design/decisions/`，说明背景、方案、取舍、状态和关联验证。
- 复发型历史坑写入 `design/regressions/`，但只有无法被测试、schema、lint 或当前 design 表达时才新增。
- 同一历史教训一旦能被自动验证覆盖，应优先删除或标记过期的 regression。
- 决策或 regression 失效时，必须标记 `Superseded`、写清替代关系，并在后续清理中删除或归档。

### 预算怎么判断

- 预算不是固定行数，而是相对项目规模：稳定边界、公开契约、核心流程、高风险历史坑越多，允许的文档和测试才相应增长。
- 超预算信号包括：同一边界多份重复文档、测试只映射实现分支、文档没有验证入口、小改动需要读大量材料、AGENTS 规则反复解释同一件事。
- 超预算时先重构：合并重叠文档、删除过期测试、把历史教训转成自动验证、把实现细节移出契约。
- 新增 design/tests/decision/regression 前，先检查是否能更新既有稳定边界，而不是再开一份新文件。
